# Как нарезать систему: флоу, блоки, сценарии

`RULES.md` — про формулировки внутри флоу. Этот документ — про структуру: **что считать флоу**, **что
считать блоком**, **как из дерева нарезаются сценарии**.

---

## 1. Флоу = один бизнес-сценарий целиком

- Флоу описывает сценарий **от первого события до итога** так, как его пережил бы пользователь или
  оператор: «Оформление заказа и оплата», «Возврат товара», «Заявка → оплаченная сделка».
- **Не «хаб по ручкам».** Флоу, собранный по принципу «все эндпоинты контроллера X», читается плохо:
  у ручек разные входы и разные итоги. Исключение — каталожный формат (`RULES.md` §9) для однотипных адресов.
- Если сценарий продолжается новым запросом (webhook, действие склада, ответ клиента) — это **второй
  `entry` в том же флоу** после `wait`, а не отдельный флоу. Разрыв на два флоу прячет самое интересное:
  что происходит между запросами.
- Сценарии, которые естественно следуют друг за другом («оплатил» → «вернул»), — разные флоу; в `what`
  второго можно написать, откуда в него приходят.

Признак хорошей нарезки: у флоу одна точка входа в `root`, понятное название на языке бизнеса и 3–6
сценариев, которые менеджер отличит друг от друга.

**Карта по документации** режется так же — по задачам человека, а не по документам: «Как получить
сертификат» собирает правила из разделов про модули, тест, проект и подписку. Флоу, который пересказывает
один документ сверху вниз, ничего не добавляет к самому документу.

---

## 2. Блок = одно наблюдаемое событие

Читатель должен уметь сказать про блок: «это уже случилось» / «на этом стоим» / «этого ещё не было».

Блоком **является**:
- вход: HTTP-ручка, запуск задачи, действие человека или внешней системы;
- решение с больше чем одним исходом;
- действие с наблюдаемым следствием: создали заказ, списали деньги, отправили КП;
- ожидание внешнего события: клиент подтверждает платёж, склад получает посылку;
- финиш: ответ получен, цепочка кончилась.

Блоком **не является**: вспомогательный вызов без исхода, DTO, конструктор, лог — и любая деталь,
которая всегда идёт вместе с соседним блоком. Это `effects`.

**Шаг вне нашего кода — тоже блок.** Если цепочку продолжает чужая система или человек (банк проводит
3-D Secure, склад вскрывает посылку), без такого блока непонятно, откуда взялись данные. `file` у него
указывает на ближайшую строку нашего кода, куда приходит результат, или отсутствует. В карте по
документации такой шаг ссылается на раздел, где описано, что делает другая сторона.

---

## 3. Дерево

1. **Один корень** (`root`) — самое раннее событие любого сценария.
2. **Ветвление описано полностью**: все исходы из кода, включая «ничего не найдено» и «внешняя система
   не ответила».
3. **Каждая ветка ведёт в блок** — в следующий шаг или в свой финиш.
4. **Финиш на каждый отдельный ответ** — по ним потом ищут причину в логах.
5. **Повторы — цикл** назад на блок попытки; лимит повторов — отдельная развилка.
6. **Этапы** (`stages`) режут дерево на 4–6 частей по смене действующего лица или фазы: проверки →
   заказ → оплата → подтверждение → итог.
7. **Актёр** — цвет блока. Красный лучше оставить сбою и не давать его актёрам.

---

## 4. Сценарии

**Сценарий — один проход от корня до конкретного финиша.** Новых блоков он не добавляет.

1. **Сценарий на каждый исход, который по-разному разбирают**: не «все сбои», а «банк отклонил»,
   «покупатель ушёл со страницы банка», «поддельный webhook» — у них разные причины и действия.
2. **Путь связный**: каждый следующий блок достижим из предыдущего по объявленной ветке. Проверяется сборкой.
3. **Сценарий кончается там, где кончается работа** — финишем.
4. **В сценарии видны только его блоки** (и запущенные ими фоновые задачи) — чужие ветки не отвлекают.
5. **«Все сценарии»** — дерево целиком; для тех, кто разбирается в устройстве флоу.
6. **Имя — на языке менеджера**, о результате: «Счёт выставлен, но не оплачен», а не «paid_timeout».

---

## 5. Порядок работы над флоу

1. Найти вход (маршрут, событие, канал, действие человека) и пройти по коду до всех возвратов — или по
   всем разделам документации, которые касаются сценария, — выписать блоки.
2. У каждой развилки перечислить все исходы; условие — дословно.
3. Фоновые задачи — `spawns`, ожидания — `wait`, повторные запросы — вторые `entry`.
4. Разложить блоки по этапам, написать подписи по `RULES.md`.
5. Нарезать 3–6 сценариев; для параллельных линий — `sub`.
6. `scan --anchors` → `scan` → `build` → открыть карту и пройти чек-лист `RULES.md` §11.
