# Инструкция для ИИ-агента: построить сценарные карты проекта

Этот файл — для любой нейросети (Claude, GPT, Gemini, локальные модели), которая будет описывать проект
картами. Прочитай его целиком, затем `docs/FORMAT.md`, `docs/RULES.md`, `docs/FLOW_TREE_RULES.md` и
пример под свою задачу:

| Задача | Режим | Пример |
|---|---|---|
| описать, как работает код репозитория | `code` | `examples/shop/flows/checkout.json` |
| объяснить проект по его документации | `docs` | `examples/academy/flows/certificate.json` |
| описать регламент со слов человека | `code` без `file` | `examples/crm/flows/lead-to-deal.json` |

## Роль и границы

- Ты **описываешь** систему, а не меняешь её. Код и документация проекта не правятся; найденные проблемы
  идут в `attention` шага.
- Условия веток (`cond`) берутся **из источника дословно**: из кода — выражение, из документации — цитата
  в кавычках «…». Не по памяти и не «как обычно бывает». Нет доступа к источнику — так и скажи и попроси
  его, а не выдумывай.
- Подписи с префиксом `custom_*` написал человек — не меняй их. Правишь только дефолтные поля.
- Готовность проверяется командами, а не на глаз: `build` без ошибок и `scan` без расхождений.

## Выбери источник

Источник задаётся полем `mode` конфига и определяет, что ты читаешь и на что ссылаются шаги:

- **`code` — карта по репозиторию.** Читаешь код: входы, ветки, коды ответов. `file` шага —
  `путь:строка` места решения в коде, `anchor` — функция. `scan` ловит правки функций.
- **`docs` — объясняющая карта по документации.** Читаешь README, вики, регламенты, спецификации
  (`.md`, `.rst`, `.adoc`, `.txt`). `file` шага — `путь:строка` раздела, где записано правило, `anchor` —
  раздел документа. `scan` ловит правки текста разделов. Код не нужен.

Режимы можно смешивать: в карте кода шаг может ссылаться на раздел документации (например, на регламент,
которым объясняется ветка), в карте документации — на функцию. `scan` понимает оба вида ссылок.
`mode` влияет на заготовки `init` и подписи главной (входные точки или разделы документации).

## Режим А. Карта по репозиторию (`mode: code`)

```bash
# 0. каркас (один раз); codeRoot — корень кода относительно каталога карт
node <kit>/bin/init.mjs docs/scenario-map --title="<Название проекта>" --code-root=../..
```

1. **Инвентаризация.** Найди все входные точки: роуты (HTTP, RPC, GraphQL), обработчики очередей и
   событий, cron, CLI-команды, webhooks. Запиши их в `entrypoints` конфига:
   `{ "group": "<раздел>", "kind": "POST", "name": "/api/checkout", "anchor": "src/checkout.js::placeOrder" }`.
   `anchor` = путь от `codeRoot` + `::` + имя функции / метода.
2. **Разделы.** Сгруппируй входы по областям системы (`groups`: заказы, кабинет, админка, интеграции…).
3. **Актёры.** Опиши в `actors`, кто действует в системе: пользователь, интерфейс, API, база, очередь,
   внешние сервисы, сотрудники. 5–8 штук, цвет — `type` из `FORMAT.md`.
4. **Нарезка на флоу.** Один флоу = один бизнес-сценарий от первого события до итога
   (`FLOW_TREE_RULES.md` §1). Начни с самого важного для бизнеса сценария.
5. **Описание флоу.** Для каждого:
   - прочитай код входа и **всех** веток до каждого `return` / `throw` / ответа;
   - выпиши блоки (`FLOW_TREE_RULES.md` §2), у развилок — все исходы с `cond` из кода;
   - каждый код ответа — свой финиш «Отказ <код> — причина»;
   - фоновые задачи — `spawns` + `next`, ожидания — `wait`, продолжение новым запросом — второй `entry`;
   - подписи — по `RULES.md` §5 (смысл в `title`, техника в `code`, развилка — вопрос, «да» по основному пути);
   - `file` = `путь:строка` места решения;
   - 3–6 сценариев в `presets`.
   Заготовка: `node <kit>/bin/init.mjs docs/scenario-map --flow=<id> --name="<Название>"`.
6. **Привязка и сборка** — см. «Проверка» ниже. «Коды ответа без финиша» в отчёте `scan` — неописанные
   исходы: добавь финиш или объясни в `what`, почему код недостижим (для этого настрой
   `scan.outcomeCodePatterns` под свой фреймворк).
7. **Отчёт человеку:** какие флоу описаны, покрытие `entrypoints` (видно на главной), список `attention`
   с краткими следствиями, что осталось неописанным.

## Режим Б. Объясняющая карта по документации (`mode: docs`)

Цель — чтобы человек, не читая всю документацию, по карте понял: **с чего начинается сценарий, какие
правила на него влияют, чем он может закончиться и где это написано.** Заодно карта показывает, где
документация противоречит себе или молчит.

```bash
# 0. каркас; codeRoot — корень документации относительно каталога карт
node <kit>/bin/init.mjs docs/scenario-map --mode=docs --title="<Название проекта>" --code-root=..
# 1. оглавление всей документации: разделы с file и anchor
node <kit>/bin/scan.mjs --project=docs/scenario-map --outline            # или --outline=wiki --json
```

1. **Опись.** Прочитай оглавление (`--outline`) и сами документы. Разделы, которые описывают поведение
   (правила, сроки, условия, роли, исходы), запиши в `entrypoints` — по ним считается покрытие:
   `{ "group": "<раздел>", "kind": "doc", "name": "Пробный период", "anchor": "docs/onboarding.md::Пробный период" }`.
   `anchor` = путь от `codeRoot` + `::` + текст заголовка, как его печатает `--outline`. Справочные
   разделы (история изменений, глоссарий, контакты) в покрытие не включай.
2. **Разделы главной** (`groups`) — области продукта или части документации: доступ и оплата, обучение,
   администрирование.
3. **Актёры** — роли из документации: пользователь, сотрудник, система, внешний сервис. Заготовка
   `init --mode=docs` даёт `user`, `team`, `system`, `data`, `process`, `external` — переименуй под проект.
4. **Нарезка на флоу.** Один флоу = одна задача человека, которую объясняет документация: «как получить
   сертификат», «что будет, если не заплатить», «как проходит согласование договора». Хороший флоу
   собирает правила из **нескольких** разделов и документов в один путь — это и есть польза карты.
5. **Описание флоу:**
   - `entry` / первый шаг — с чего начинает человек; второй `entry` — когда он возвращается позже
     (новая попытка, ответ другой стороны);
   - развилка — правило документации с разными исходами: «Тест сдан на 70 баллов и выше?»;
   - `cond` — **цитата** из документа в «…»: `«не ниже чем на 70 баллов из 100»`; ветка «иначе» — `иначе`;
   - сроки и ожидания — шаги `wait` («Ждём: куратор проверяет проект»), лимиты повторов — отдельная развилка;
   - `file` — `путь:строка` строки, где записано правило (номер строки — из `--outline` или из файла);
   - `code` — короткая ссылка для читателя: `certificates.md → Итоговый тест`;
   - каждый исход, который документация различает, — свой финиш: «Финиш: …», «Тупик: …», «Отказ — …».
6. **`attention` — главное в этом режиме.** Сюда идут:
   - **противоречия** между документами: «onboarding.md — 14 дней, billing.md — 7 дней» — с обеими ссылками;
   - **пробелы**: у развилки описан только один исход, нет срока, нет ответственного, не сказано, что
     будет при сбое;
   - **неоднозначности**, из-за которых разные люди поступят по-разному.
   Формулировка — со следствием для читателя: не «не описано», а «студент будет ждать сертификат,
   которого не будет». Чего в документации нет — того нет на карте: пробел не заполняется догадкой,
   он становится `attention`.
7. **Проверка** — см. ниже. Для этого режима полезно `rules.requireFile: true`: каждый шаг обязан
   ссылаться на документ.
8. **Отчёт человеку:** какие флоу описаны, покрытие разделов (видно на главной), **список противоречий
   и пробелов** с местами в документах, какие разделы не попали ни в один флоу.

## Проверка (оба режима)

```bash
node <kit>/bin/scan.mjs  --project=docs/scenario-map --anchors   # anchor + fingerprint
node <kit>/bin/scan.mjs  --project=docs/scenario-map             # должно быть «Расхождений нет»
node <kit>/bin/build.mjs --project=docs/scenario-map             # «данные целостны», exit 0
```

Ошибки сборки перечислены списком `<флоу>: <шаг>: <что не так>` — исправь данные и пересобери.

### Сопровождение после изменений кода или документации

`scan` → для каждого «МЕТОД ИЛИ РАЗДЕЛ ИЗМЕНИЛСЯ» перечитай функцию или раздел и проверь шаг и его
ветки → поправь данные → `scan --anchors` → `build`. «ШАГ ОСИРОТЕЛ» — найди, куда переехала логика или
текст (раздел переименовали — поменялся `anchor`), обнови `file`, или удали шаг. «СТРОКА ВНЕ СИМВОЛА» —
обнови номер строки в `file`.

## Без доступа к файлам: только чат

Человек вставляет код или текст документации, ты возвращаешь JSON флоу, человек кладёт его в
`flows/<id>.json` и запускает сборку. Готовый промпт — ниже; человек копирует его целиком и добавляет
источник.

```text
Ты пишешь сценарную карту для инструмента scenario-map-kit. Верни ОДИН JSON-объект флоу, без пояснений.
Источник — код или документация (ниже). Всё, что на карте, должно следовать из источника.

Формат:
{ "id": "<латиница>", "order": 1, "name": "<название сценария>", "group": "<id раздела>",
  "tone": "ok", "entry": "<адрес, событие или действие человека>", "what": "<2–3 предложения>",
  "root": "<id первого шага>", "strict": true,
  "stages": { "<ключ>": "<этап>", ... },
  "steps": { "<id>": { "kind": "entry|step|branch|wait|terminal", "actor": "<актёр>", "stage": "<ключ>",
      "title": "...", "code": "...", "file": "<путь:строка>", "what": "...", "effects": ["..."],
      "attention": ["..."], "next": "<id>" | "branches": [ { "short": "...", "hint": "...",
      "cond": "<условие из кода дословно или цитата «…» из документации>", "to": "<id>", "tone": "ok|bad|warn|info" } ],
      "spawns": ["<id корня фоновой линии>"], "outcome": "ok|bad|warn|info" } },
  "presets": [ { "name": "...", "tone": "ok", "note": "...", "path": ["<root>", "...", "<финиш>"],
      "sub": ["<корень фоновой линии>", "...", "<её финиш>"] } ] }

Правила:
1. Один шаг = одно решение или одно действие. Проверки подряд с разными исходами — разные шаги.
2. title — смысл человеческим языком; имя функции или раздела — в code. Развилка — вопрос, «да» ведёт по основному пути.
3. У каждой ветки: short (≤14 символов, сам ответ), hint (≤34, почему), cond (дословно из источника).
4. Каждый различимый исход — отдельный terminal: «Отказ <код> — причина», «Финиш: <что получилось>», «Тупик: <почему>».
5. terminal без next/branches, но с outcome. Хотя бы один outcome "ok".
6. Запуск фоновой задачи — spawns + next (не развилка). Цель spawns недостижима обычными переходами.
7. Ожидание человека или внешней системы — шаг wait. Продолжение новым запросом или возвращение человека — ещё один entry.
8. Повтор — ветка назад на уже описанный шаг; лимит повторов — отдельная развилка.
9. Проблемы — в attention со следствием: в коде (мёртвая ветка, нет защиты от повтора), в документации
   (противоречие между разделами, не описан исход, нет срока или ответственного).
10. 3–6 presets: основной путь, типовые отказы, краевые случаи. path — непрерывная цепочка от root до terminal.
11. Все шаги достижимы от root или от корней spawns. Ничего не выдумывай: чего нет в источнике — нет на карте.

Актёры проекта: <список id и что они значат>
Раздел (group): <id>
Источник (код или документация с номерами строк):
<вставить>
```

После ответа модели: сохранить в `flows/<id>.json`, запустить `node bin/build.mjs --project=…` и, если
сборка вернула ошибки, отдать их списком той же модели — «исправь JSON по этим ошибкам».

## Частые ошибки агентов

| Ошибка | Как правильно |
|---|---|
| Развилка «Товара нет?» — «да» ведёт в отказ | «Все товары есть на складе?» — «да» по основному пути |
| Один финиш «Ошибка» на все отказы | финиш на каждый код: 409, 422, 402 |
| Диспатч джобы как развилка «запустить / нет» | `spawns` + `next` у шага, который её ставит |
| Письмо-уведомление отдельной линией | `effects` шага |
| `cond: "если товар есть"` | `cond: "missing.length === 0"` — дословно |
| Webhook отдельным флоу | второй `entry` после `wait` в том же флоу |
| `anchor` / `fingerprint` написаны руками | их ставит `scan --anchors` |
| Пересказ кода построчно в `what` | 1–3 предложения: что решается и почему важно |
| Флоу = пересказ одного документа по порядку | флоу = задача человека; правила собираются из разных разделов |
| `cond: "если сдал тест"` в карте по документации | `cond: "«не ниже чем на 70 баллов из 100»"` — цитата |
| Пробел в документации закрыт «здравым смыслом» | пробел — `attention` со следствием, на карте только написанное |
| Противоречие описано одной ссылкой | обе цитаты и оба файла в тексте `attention` |
